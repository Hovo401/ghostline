# Ghostline — продуктовые и технические требования

> Статус: черновик v0.2 · 2026-09-28 — добавлены функции из прототипа дизайна (Ghostline.dc.html)
> Стиль, анимации, 3D и система тем — в [DESIGN-BRIEF.md](DESIGN-BRIEF.md).

## 1. Видение

**Ghostline** — веб-мессенджер «для своих»: работает в браузере, без установки и без номера телефона. Сначала — для себя и друзей на собственном сервере, затем — open-source проект, который любой может развернуть одной командой `docker compose up`.

Логика работы как у Telegram, но только ядро: личные чаты и группы, текст, медиа, файлы, голосовые сообщения, видео-кружки и исчезающие сообщения. Без рекламы, ленты и рекомендаций. Отличие — дизайн: спокойный интерфейс с «цифровым шумом», 3D-сценой на главной и гибкой настройкой внешнего вида (темы, акценты, шрифты, своя тема).

### Цели MVP

- Переписка в реальном времени: личные чаты и группы.
- Фото, видео, файлы, голосовые сообщения и видео-кружки.
- Исчезающие сообщения с таймером для каждого чата.
- Регистрация без номера и email: имя пользователя, пароль и фраза восстановления.
- Home page с 3D-сценой, которая вызывает «вау».
- Полная настройка внешнего вида: 6 тем + своя, 7 акцентов + свой, 4 шрифта, размер текста, форма пузырей. Новые темы добавляются без переписывания компонентов.
- Развёртывание одной командой через Docker Compose.

### Осознанно не входит в MVP

| Что | Почему / когда |
|---|---|
| Сквозное шифрование (E2E) | Сильно усложняет всё: несколько устройств, поиск, медиа. Решение — до v1, см. §8 |
| Групповые звонки | 1:1 аудио/видео — см. §5.14. Групповые требуют SFU-комнату на N участников — Later |
| Каналы, боты, стикеры, секретные чаты | Later |
| Нативные мобильные приложения | Вместо них — адаптивный веб, с v1 — PWA |
| Федерация между серверами | Не планируется |

## 2. Роли

| Роль | Кто | Что может |
|---|---|---|
| Гость | Не авторизован | Смотреть Home, входить, регистрироваться (по инвайту, если так настроено) |
| Пользователь | Зарегистрирован | Всё в мессенджере |
| Администратор инстанса | Владелец сервера: первый зарегистрированный или заданный в env | Инвайты, пользователи, лимиты |
| Роли в группе | Владелец / админ / участник | См. §5.5 |

## 3. Приоритеты

- **MVP** — нужно, чтобы позвать друзей.
- **v1** — первая полноценная версия, до выхода в open source.
- **Later** — идеи на потом. Архитектура не должна им мешать.

### 5.7 Медиа и файлы

| ID | Требование | Приоритет |
|---|---|---|
| FR-MEDIA-01 | Фото (JPEG, PNG, WebP, GIF): до 10 в одном сообщении, сетка-альбом, подпись | MVP |
| FR-MEDIA-02 | Видео (MP4, WebM, MOV): превью-кадр, длительность, встроенный плеер. Отдельный тип сообщения `video` — обычное видео из галереи/файла, в отличие от `video_note` (круглый видео-кружок, FR-VOICE-06), которое остаётся кружком | MVP |
| FR-MEDIA-03 | Файлы любого типа: иконка по типу, имя, размер, скачивание. Скачивание доступно для любого типа вложения (фото, файл, голосовое, видео, видео-кружок), не только из полноэкранного просмотрщика; для текстовых файлов (txt/md/log/json/csv) — кнопка «Просмотр» текста | MVP |
| FR-MEDIA-04 | Лимит размера файла задаётся в env (`MEDIA_MAX_FILE_SIZE_BYTES`), по умолчанию 1 ГБ. Файлы больше 16 МиБ загружаются частями (multipart): `POST /attachments/presign` возвращает `mode: "single"` (обычный presigned `PUT`) или `mode: "multipart"` (`partSize`/`partCount`); части презентуются по запросу через `POST /attachments/:id/parts`, а `POST /attachments/:id/complete` завершает загрузку через серверный `ListParts` (docs/adr/0010) | MVP |
| FR-MEDIA-05 | Прикрепить можно через скрепку (меню «Фото или видео» / «Файл»), перетаскиванием в чат и вставкой из буфера (`Ctrl+V`) | MVP |
| FR-MEDIA-06 | Предпросмотр перед отправкой: список вложений, удаление, подпись, выбор «сжать» или «отправить файлом» | MVP |
| FR-MEDIA-07 | Прогресс загрузки, отмена (`DELETE /attachments/:id` — отменяет multipart и удаляет незавершённую загрузку), повтор после ошибки. Загрузка продолжается при переключении между чатами | MVP |
| FR-MEDIA-08 | До загрузки картинки — размытый плейсхолдер (thumbhash) правильных пропорций, чтобы лента не прыгала | MVP |

## 6. Нефункциональные требования

### 6.1 Производительность

- Открытие чата из кэша — до 100 мс, с сервера — до 400 мс (p95).
- От отправки до появления у получателя — до 300 мс (p95, один сервер).
- Лента сообщений и список чатов виртуализированы (TanStack Virtual): 60 fps при прокрутке истории из 10 000+ сообщений.
- Начальный JS мессенджера — до 300 КБ gzip. Three.js и 3D-сцена — отдельный ленивый чанк только для публичных страниц; в `/app` он не загружается.
- Картинки отдаются в размерах под место показа (например, WebP 320 / 800 / 1600 px), оригинал — по запросу.

### 6.2 Надёжность доставки

- У каждого сообщения есть `clientMessageId` (UUID, создаёт клиент): повторная отправка того же сообщения не создаёт дубль.
- Внутри чата у сообщений есть монотонный номер `seq`. Клиент помнит последний `seq`, после переподключения запрашивает всё, что после него.
- Порядок сообщений определяет сервер.

### 6.3 Безопасность

- Пароли хэшируются argon2id.
- HTTPS обязателен (в compose — nginx; сертификаты Let's Encrypt через certbot). Это нужно не только для безопасности: браузеры дают доступ к микрофону и камере только на HTTPS или `localhost`. Без HTTPS друзья не смогут записать голосовое.
- Фраза восстановления: только хэш argon2id; вход по фразе — не больше 5 попыток в час на username и на IP; после успешного входа по фразе выдаётся новая фраза.
- Refresh-токены хранятся в БД в виде хэша. Если старый токен используют повторно, отзывается вся цепочка сессии.
- Ограничение частоты запросов: вход, регистрация, отправка сообщений, загрузки.
- Проверка доступа на каждый запрос и каждое WebSocket-событие: пользователь должен быть участником чата.
- Бакет S3 приватный. Скачивание — через короткоживущие подписанные URL, выдаваемые после проверки доступа.
- Тип файла определяется по содержимому (magic bytes), а не по расширению. SVG, HTML и подобные отдаются только на скачивание (`Content-Disposition: attachment`).
- Текст сообщений никогда не рендерится как HTML. CSP, helmet, CORS только для своего домена.
- Все входные данные валидируются zod-схемами, общими для фронтенда и бэкенда.
- Пока нет E2E, интерфейс и тексты на сайте не утверждают, что переписка зашифрована end-to-end. Шифрование при передаче (TLS) при этом есть.

### 6.4 Совместимость

- Браузеры: последние две версии Chrome/Edge, Firefox, Safari (macOS и iOS).
- Экраны от 360 до 2560 px.
- iOS Safari: запись аудио и видео через MediaRecorder в MP4, воспроизведение нормализованных форматов.

### 6.5 Доступность

- Контраст по WCAG 2.2 AA во всех темах (проверяется автотестом, см. DESIGN-BRIEF §8.3). Для своей темы — предупреждение при низком контрасте.
- Полная работа с клавиатуры, видимый фокус, подписи для скринридеров.
- Учитывается `prefers-reduced-motion`; есть ручная настройка уровня анимаций.

### 6.6 Интернационализация

- Все строки интерфейса — через i18n (i18next), с первого дня русский и английский. Даты и время — в формате локали.
- Шрифты поддерживают кириллицу.

### 6.7 Масштабируемость

- MVP: один экземпляр backend и один воркер. Ориентир — до ~100 пользователей, до ~50 одновременно онлайн.
- Горизонтальное масштабирование — без переписывания: API без состояния, присутствие в Redis, Redis-адаптер для Socket.IO.

### 6.8 Эксплуатация

- Структурированные логи (pino), эндпоинты `/health` и `/ready`.
- Миграции БД — Prisma Migrate, применяются при старте контейнера.
- Конфигурация — только через env; `.env.example` и проверка переменных при старте.
- Резервное копирование: дамп Postgres и копия бакета по расписанию (v1).

### 6.9 Качество

- TypeScript в strict-режиме на фронтенде и бэкенде, ESLint + Prettier.
- CI (GitHub Actions): линт, проверка типов, тесты, сборка Docker-образов.
- Тесты: unit (Vitest), e2e API на тестовой БД в Docker, e2e UI (Playwright) для ключевого сценария: регистрация → чат → текст, фото, голосовое.

### 6.10 Готовность к open source

- Лицензия (§8), README, CONTRIBUTING, гайд по self-host, гайд «как сделать свою тему».
- Никаких секретов в репозитории. Внешние сервисы подключаются через env и заменяемы: любой S3-совместимый провайдер, любой SMTP.

## 7. Архитектура

### 7.1 Структура репозитория

Монорепозиторий на pnpm workspaces: у фронтенда и бэкенда общие схемы и типы (DTO, события WebSocket), поэтому контракт между ними не расходится.

```
chat/
├─ backend/              NestJS: REST API, WebSocket-шлюз, воркер
├─ frontend/             React SPA (Vite)
├─ packages/
│  └─ contracts/         zod-схемы, DTO, типы WS-событий — общие для фронта и бэка
├─ docker/               конфиг nginx, init-скрипты
├─ docs/
├─ docker-compose.yml        прод и self-host
└─ docker-compose.dev.yml    переопределения для разработки (hot reload, mailpit)
```

### 7.2 Сервисы Docker Compose

| Сервис | Образ | Назначение |
|---|---|---|
| `nginx` | nginx + certbot | Reverse proxy, HTTPS (Let's Encrypt), раздача собранного SPA. `/` → статика, `/api` → backend, `/socket.io` → backend с проксированием WebSocket (`Upgrade`/`Connection`), отдельный поддомен (например `s3.domain`) → MinIO — браузер загружает файлы по подписанным URL напрямую в хранилище, мимо backend |
| `backend` | Node 24 LTS | NestJS: REST API и Socket.IO |
| `worker` | тот же образ, другая команда | Фоновые задачи (BullMQ): превью, транскодирование (ffmpeg, sharp), очистка |
| `postgres` | postgres:18 | Основная БД |
| `redis` | Redis или Valkey | Очереди BullMQ, присутствие, лимиты запросов, адаптер Socket.IO |
| `minio` | S3-совместимое хранилище | Медиа и файлы. В проде заменяется на AWS S3, Cloudflare R2 и т.п. — код работает только через S3 API |
| `mailpit` | только для разработки | Перехват писем (v1) |

Два дополнения к исходному стеку:

- **Redis** — без него неудобно делать очередь обработки медиа, присутствие и масштабирование сокетов.
- **MinIO** — в 2025 году компания меняла условия распространения бесплатной версии. Перед стартом проверить актуальный статус образа; альтернативы — Garage, SeaweedFS.

### 7.3 Backend (NestJS)

| Модуль | Ответственность |
|---|---|
| `auth` | Регистрация, вход, токены, сессии, инвайты |
| `users` | Профиль, поиск, конфиденциальность, блокировки |
| `chats` | Чаты, группы, участники, роли |
| `messages` | Сообщения, `seq`, реакции, закрепы, прочтения |
| `media` | Подписанные URL для загрузки, завершение загрузки, ссылки на скачивание |
| `realtime` | Socket.IO-шлюз: аутентификация сокета, комнаты, рассылка событий |
| `presence` | Онлайн, последний визит, «печатает» |
| `settings` | Настройки пользователя, включая внешний вид |
| `calls` | Звонки 1:1: жизненный цикл (ringing/active/ended/…), токены LiveKit — см. §5.14, docs/adr/0009 |
| `notifications` | Web Push: подписки, настройки, рассылка (сообщения и звонки) — см. docs/adr/0010 |
| `admin` | Инвайты, пользователи, статистика |
| `jobs` (воркер) | Обработка медиа, очистка незавершённых загрузок, удаление файлов удалённых сообщений |

Принципы:

- **Изменения — через REST, доставка — через WebSocket.** Отправить, изменить, удалить, отметить прочитанным — REST-запросы: проще валидация, идемпотентность, повторы и тесты. WebSocket — канал событий от сервера к клиенту и эфемерные события от клиента («печатает»).
- После коммита транзакции сервис публикует доменное событие (`message.created`), модуль `realtime` рассылает его участникам. Внутри одного процесса — EventEmitter, при масштабировании — Redis pub/sub.
- События адресуются в комнаты пользователей `user:{id}` — туда подключены все устройства пользователя. Не нужно синхронизировать членство в комнатах при добавлении и удалении из группы.
- API версионируется (`/api/v1`), OpenAPI-документация генерируется автоматически.

Ключевые решения:

- **Прочтения — через `ChatMember.lastReadSeq`**, а не отдельную запись на каждое сообщение. Сообщение прочитано, если его `seq ≤ lastReadSeq` у собеседника. Аналогично «доставлено» через `lastDeliveredSeq`.
- **`seq` выдаётся атомарно** в той же транзакции, что и вставка: `UPDATE chat SET last_seq = last_seq + 1 RETURNING last_seq`.
- **Удаление у всех — мягкое.** Текст и вложения стираются, остаётся «надгробие», чтобы все клиенты синхронизировались. Файлы из S3 удаляет воркер.
- **Удаление у себя** — отдельная таблица скрытых сообщений `(userId, messageId)` (v1).
- **Исчезающие сообщения.** `expiresAt` фиксируется при отправке — смена таймера не влияет на уже отправленные. Воркер раз в ~10 с удаляет истёкшие (как «удаление у всех», но без надгробия) и рассылает `message:deleted`; клиент дополнительно прячет сообщение сам ровно в `expiresAt`, не дожидаясь сервера.
- **Приватность проверяется на сервере.** Если у получателя выключены отчёты о прочтении, сервер не рассылает `read:updated` его собеседникам; если выключен «в сети» — `presence` отдаёт только «был недавно». Клиентские флаги — только для отображения.
- **Текст + сущности вместо Markdown** — безопасный рендер, простой поиск, та же модель, что в Telegram.

### 7.5 Realtime-протокол (Socket.IO)

Подключение: access-токен передаётся в `auth` при рукопожатии. Когда токен истекает, клиент обновляет его и переподключается.

| Направление | Событие | Данные |
|---|---|---|
| сервер → клиент | `message:new` | Сообщение целиком |
| сервер → клиент | `message:updated` | Правка, реакции, медиа готово |
| сервер → клиент | `message:deleted` | `chatId`, `messageId` |
| сервер → клиент | `chat:updated` | Информация, участники, роли |
| сервер → клиент | `chat:removed` | Пользователя удалили из чата или чат удалён |
| сервер → клиент | `read:updated` | `chatId`, `userId`, `lastReadSeq` |
| сервер → клиент | `delivered:updated` | `chatId`, `userId`, `lastDeliveredSeq` — сообщение доставлено (галочка «доставлено» у отправителя) |
| сервер → клиент | `presence` | `userId`, `online`, `lastSeenAt` |
| сервер → клиент | `typing` | `chatId`, `userId`, `action`: `typing` / `voice` / `video` |
| сервер → клиент | `call:incoming` | Звонок целиком (§5.14) — новый входящий звонок |
| сервер → клиент | `call:updated` | Звонок целиком — смена статуса (принят/отклонён/завершён/…), в т.ч. на других вкладках того же пользователя (FR-CALL-09) |
| клиент → сервер | `typing` | `chatId`, `action` (не чаще раза в 3 с) |

Синхронизация после переподключения:

- **MVP:** клиент перезапрашивает список чатов (в нём `lastSeq` каждого чата). Если в открытом чате локальный `seq` меньше серверного — догружает `GET /chats/:id/messages?afterSeq=`. Правки старых сообщений, пропущенные в офлайне, видны после перезагрузки истории.
- **v1:** журнал изменений чата с отдельным счётчиком (как `pts` в Telegram) — точная синхронизация правок и удалений.

### 7.6 Загрузка медиа

1. Клиент: `POST /api/v1/attachments/presign { kind, mime, size, fileName }`. Сервер проверяет `size` против `MEDIA_MAX_FILE_SIZE_BYTES` (FR-MEDIA-04, по умолчанию 1 ГБ) — иначе 413 — создаёт `Attachment` со статусом `PENDING` и отвечает одним из двух режимов:
   - `size ≤ 16 МиБ` (`MULTIPART_THRESHOLD_BYTES`, `packages/contracts`): `{ mode: "single", uploadUrl }` — как раньше, один подписанный `PUT`;
   - `size > 16 МиБ`: `{ mode: "multipart", partSize, partCount }` — сервер уже открыл multipart-загрузку в S3 (`CreateMultipartUpload`) и сохранил `uploadId` на `Attachment`.
2. Клиент загружает файл напрямую в S3, показывая прогресс. Backend не пропускает через себя байты файла. Для `multipart` клиент режет файл на части по `partSize` и для каждой партии частей запрашивает подписанные `PUT`-URL через `POST /api/v1/attachments/:id/parts { partNumbers }` (до 20 за раз, TTL 15 мин) — URL выдаются по мере надобности, а не все сразу, чтобы долгая загрузка не упёрлась в истёкшие ссылки для последних частей (docs/adr/0010).
3. Клиент: `POST /api/v1/attachments/:id/complete`. Для `multipart`-загрузки сервер сначала сам вызывает `ListParts` (а не доверяет ETag из браузера — см. docs/adr/0010) и завершает загрузку (`CompleteMultipartUpload`). В обоих режимах сервер затем проверяет, что объект действительно появился в S3 (`HeadObject`) и что его размер совпадает с заявленным при `presign` (иначе 400 — файл соврал о размере или загрузка повреждена), помечает `Attachment` как `READY` и ставит задачу обработки в очередь (сам воркер — no-op заглушка до отдельной задачи на thumbnails/транскодинг).
4. Клиент отправляет сообщение (`POST /api/v1/messages`) с `attachmentId` — только владелец вложения и только когда оно `READY` (иначе 404/409). Сообщение сразу несёт вложение целиком (mime/name/size/размеры/URL) в поле `attachment`, а не только `attachmentId` — см. следующий пункт.
5. Отмена незавершённой загрузки: `DELETE /api/v1/attachments/:id` — только для своего `PENDING`-вложения; прерывает multipart-загрузку в S3 (`AbortMultipartUpload`), лучшим усилием удаляет объект и удаляет саму запись.
6. Скачивание: **не** отдельный `GET /api/v1/media/:id`-редирект — каждый `Attachment` в ответе API/WS-пуше (`GET /messages`, `message:new`, …) уже несёт свежий подписанный GET URL (`attachment.url`, живёт `PRESIGN_DOWNLOAD_TTL_SECONDS` ≈ 10 мин), посчитанный на лету при сериализации ответа. Почему не редирект — см. docs/adr/0007-embed-presigned-media-urls.md (кратко: `<img>`/`<audio>`/`<video>` не могут послать `Authorization`-заголовок на редиректящий эндпоинт). Для сообщений старше ~10 минут (или когда нужно просто скачать/открыть вложение вне контекста сообщения) — `GET /api/v1/attachments/:id` выдаёт свежий `Attachment` с новым подписанным URL; доступ есть у загрузившего и у любого участника чата, где есть сообщение с этим вложением (docs/adr/0010, дополняет 0007). `Content-Disposition` кодируется по RFC 5987/6266 (`filename` + `filename*=UTF-8''...`), так что кириллические и другие не-ASCII имена файлов не ломают заголовок.
7. Незавершённые загрузки старше 24 часов удаляет воркер (не реализовано).
8. Сетка медиа в панели профиля чата (FR-CHAT-07): `GET /api/v1/chats/:id/media` — до 30 последних `READY`-вложений медиа-сообщений чата (фото/файл/голосовое/видео, `TEXT` исключены), новые сначала, в том же виде `Attachment`, что и `Message.attachment` (та же `toWireAttachment`/подписанный `url`). Доступ проверяется как у остальных `chats`-маршрутов (только участник чата).

| Тип | Что делает воркер |
|---|---|
| Фото | Превью WebP 320 / 800 / 1600 px (sharp), thumbhash, удаление EXIF, размеры |
| Видео | Постер, длительность, размеры (ffprobe); перекодирование в H.264/AAC MP4, если исходник играет не везде |
| Голосовое | Приведение к единому формату. Кандидат — AAC в M4A; подтвердить проверкой в целевых браузерах |
| Видео-кружок | Квадрат 480×480, H.264/AAC MP4, постер |
| Аватар | WebP 64 / 160 / 640 px |

## 10. Прототип дизайна и требования

Прототип `Ghostline.dc.html` — источник правды по внешнему виду. Всё, что в нём работает, входит в MVP (см. выше). Исключения и пробелы:

**Не переносим в продукт:**

| Что в прототипе | Почему |
|---|---|
| Случайное «печатает» в других чатах каждые 8 с | Демонстрация; в продукте — только настоящие события |
| Автоответы собеседника и фейковая смена статусов | Имитация сервера |
| Переключатели «Главная / Вход / Чаты / Вид», «Десктоп / Телефон», «HERO A/B/C» в верхней панели | Инструменты прототипа |
| Остатки кода «Код безопасности» / «Проверено» | Это функция E2E-шифрования, которого нет (§8, вопрос 5) |
| Шрифты с Google Fonts | В продукте шрифты локальные (§6.3) |

**Нужно в MVP, но в прототипе экрана нет — дорисовать в том же стиле:**

- Создание личного чата и группы (кнопка «Новый»), управление участниками и ролями.
- Действия с сообщением: контекстное меню, ответ, редактирование, удаление, копирование.
- Предпросмотр вложений перед отправкой, прогресс загрузки, полноэкранный просмотрщик медиа.
- Разделители дат и «Новые сообщения», кнопка «вниз».
- Системные сообщения (смена таймера, добавление участника).
- Вход по фразе восстановления (`/recover`), перевыпуск фразы.
- Разделы настроек: Конфиденциальность, Уведомления, Устройства, О приложении.
- Админка: инвайты и пользователи.
- Состояния: пустые, загрузка, ошибка отправки, потеря связи, 404.
